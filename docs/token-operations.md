# Personal token operations for local MCP users

This runbook covers `ssff-mcp key generate` and the operator steps around it:
issuing, storing, rotating and revoking the personal tokens that authenticate
fixed local MCP users (Phase 1). Tokens are high-entropy random values
generated by the system — there are **no passwords** — and the server stores
only their SHA-256 hashes. Phase 2 will add IAS as an identity provider; local
users and these procedures stay.

> **The token is shown exactly once, at generation.** There is no way to
> recover it later. If it is lost, rotate: issue a new token and revoke the
> old record.

## Quick path: issue a token

1. Generate the token and copy it **now**, from the single JSON line printed:

   ```bash
   ssff-mcp key generate
   {"token":"ssff_pat_<random>","tokenHash":"<sha256-hex>"}
   ```

2. Store **only `tokenHash`** in the server config, inside a new token record
   for the intended user. Never store the cleartext token in server configuration.
   The client needs the token in its private credential store.

3. Hand the token to the user through a secret manager or another private
   channel — never email, chat or Git.

The generator takes no options and no input, does not choose a user, and never
modifies stored configuration: mapping the hash to a user, role and expiry is
the operator's explicit edit. There is no admin UI.

## Configuration shape

Under each tenant, local users are stable records with one declared role and
their own token list:

```json
"<tenant-placeholder>": {
  "users": {
    "<user-id-placeholder>": {
      "role": "<role-placeholder>",
      "enabled": true,
      "tokens": [
        {
          "id": "<token-id-placeholder>",
          "hash": "<sha256-hex-from-key-generate>",
          "expiresAt": "<ISO-8601-date-placeholder>",
          "revoked": false
        }
      ]
    }
  }
}
```

- `expiresAt` is required: every token has a lifetime; an expired token is
  rejected like a revoked one.
- Each authenticated request is checked against the **current** configuration:
  expiry, `revoked` and `enabled` take effect on the next request, even for a
  session that is already open.
- Hashes are SHA-256 hex digests — safe to store because the token is a
  generated 256-bit random value, not a password. Never reuse this scheme for
  user-chosen secrets.

## Rotate a token

Rotation replaces a credential without a gap in service:

1. `ssff-mcp key generate` — new token, new hash.
2. Add the new token record (`id`, `hash`, `expiresAt`, `revoked: false`) to
   the user's `tokens` **atomically**: write the full updated config to a
   temporary file and rename it into place, so the server never reads a
   half-edited file.
3. Give the user the new token and switch the client to use it.
4. Set `revoked: true` on the old token record (or remove the record).

Until step 4, both tokens are valid; after it, the old token is rejected on
its next request. Rotation never changes the user's identity or role: a
session stays bound to tenant, user and authentication method, not to the
individual token.

## Disable a user or revoke access

- **Disable, keep the records:** set `enabled: false` on the user. All their
  tokens are rejected immediately; flipping it back to `true` re-enables them.
- **Revoke one token:** set `revoked: true` on that token record, or remove
  the record entirely. Either way the token stops working on the next request.
- **Remove all access:** disable the user and revoke (or remove) every token
  record.

## Security rules

- **HTTPS only in production.** Tokens must never cross a public network in
  cleartext; localhost-only development may use HTTP.
- **No client passwords.** Clients authenticate with a generated token;
  nothing else. The shared SAP technical account stays on the server.
- **Never put a token in shell history or process arguments.** Pipe secrets
   through stdin (`ssff-mcp key hash < file`), reference environment
   variables, and let clients read tokens from their secret store. Command
   lines are visible in process listings.
- **Hashes only in server config.** The hashes do not disclose generated tokens,
  but the same file may contain SSFF credentials or secret-provider references:
  a configuration leak is still a security incident.

Client examples use placeholders on purpose — resolve them with the client's
documented secret/environment mechanism, never commit real values. This is the
HTTP header shape, not a client-independent interpolation syntax:

```http
Authorization: Bearer ${SSFF_MCP_TOKEN}
```
